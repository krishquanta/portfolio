## Problem
Automotive telemetry generated by modern onboard vehicle diagnostics (OBD-II standard) outputs standardized Diagnostic Trouble Codes (DTCs) like `P0300` or `P0420`. However, raw error codes lack real-time context: they do not correlate live sensor data (mass airflow, oxygen sensor voltages, fuel trims) with vehicle service histories or repair manuals. Vehicle owners and technician apprentices struggle to prioritize faults without deciphering thousands of pages of proprietary technical service bulletins (TSBs).

## What Was Built
An intelligent diagnostic engine that accepts CAN-bus / OBD-II telemetry streams, parses raw PID hex values, and combines deterministic rule checks with semantic retrieval over repair manuals:

1. **OBD-II Telemetry Parser**: Decodes Mode 01 PID sensor payloads (coolant temperature, engine RPM, short/long-term fuel trim) and Mode 03 stored trouble codes.
2. **Contextual Retrieval Augmented Engine**: Indexes manufacturer workshop manuals and NHTSA safety bulletins into a vector database (ChromaDB) with domain-adapted embeddings.
3. **Diagnostic Reasoning Agent**: Synthesizes live sensor anomalies alongside retrieved service bulletins to generate step-by-step diagnostic verification flows (e.g., verifying vacuum leak vs. fuel injector failure for lean codes).

## System Architecture

```
[OBD-II CAN Stream] ───> [PID Hex Parser & Normalizer]
                                    │
                                    ▼
       [Live Sensor Anomalies] ───> [Context Synthesizer]
                                           ▲
                                           │
  [Manufacturer TSBs & Manuals] ───> [ChromaDB Vector Store]
                                           │

```

## Tech Used
- **Backend**: Python 3.11, FastAPI, Pydantic
- **AI & Retrieval**: PyTorch, Sentence-Transformers, ChromaDB, Hugging Face
- **Data Protocols**: SAE J1979 / ISO 15765-4 (OBD-II standard definitions)
- **Deployment**: Docker, Uvicorn, SQLite/PostgreSQL

## Key Decisions & Engineering Challenges
- **False Positive Mitigation**: LLMs hallucinate diagnostic probabilities when given raw unparsed logs. Implemented a strict two-stage pipeline: deterministic physical boundary checks (e.g., fuel trim > +10% indicates lean condition) run first to validate physical plausibility before passing query parameters to the semantic retriever.
- **Embedding Domain Specificity**: Off-the-shelf general embeddings performed poorly on dense automotive acronyms (DTC, MAF, O2S, CKP). Fine-tuned embedding tokenization on automotive repair terminology to ensure accurate recall across technical bulletins.
- **Latency Optimization**: Cached static DTC lookup tables in memory, keeping cold response times under 120ms for common sensor codes.
